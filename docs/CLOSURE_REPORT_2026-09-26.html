TryingOpen2API 终局闭环总审计 · 第 4 轮

日期：2026-09-26 · 基线：main@10f0247（v0.1.10）· 模式：4 只读审计子代理并行 + 主线程复核 + 分主题修复 + 真实验收

一、上下文与直觉（为什么做这轮）

项目已在生产环境公网部署（Azure + nginx HTTPS + systemd + CD 自动发布）。最终用户/调用方/部署者都会真实接触它。因此本轮不是「再查几个小漏洞」，而是把整个网关当作即将交付的成熟 SaaS 做一次最严格的终局审计：从架构/数据流、生产安全、前端契约/UX、盲点扫描四个正交视角并行审计，每个发现都必须有 文件:行号 证据，修复必须经过真实验收（单测、HTTP 烟测、限流/鉴权实测），而不是嘴上闭环。

直觉：「看起来能用」和「真实可用」之间隔着大量边界——日志脱敏在多字节 key 上会 panic、非流式接口把上游错误当成功返回、Anthropic 流错误后不给终止事件、面板首次打开默认 401……这些都是真实用户会踩、真实调用方会挂起的坑。

二、审计方法（并行工作流）

  • 子代理 A（架构/数据流）：请求→上游→响应全链路、并发安全、SSE 解析、占位符/死代码 → docs/audit/A4
  • 子代理 B（生产安全）：鉴权/SSRF/凭据/限流/DoS/部署面 + git 全历史密钥扫描 → docs/audit/B4
  • 子代理 C（前端/契约/UX）：面板 JS 与后端字段逐项核对、假功能、移动端 → docs/audit/C4
  • 子代理 D（盲点/文档资产）：未知未知扫描、版本漂移、sqlite 空壳、防重复台账 → docs/audit/D4
  • 主线程：复核证据 + 分主题修复（Batch-1~5）+ 门禁/HTTP/协议单测验收
