## 瓶颈定位
1. **上游生成延迟主导**（4-58s/请求）：tryingopen.com 模型生成本身慢，网关只做透传。
   不是网关瓶颈，但影响用户体验 → 建议客户端用流式（已支持）。
2. **无效模型 fallback 也走完整上游调用**：请求不存在模型 → 降级到默认模型 → 上游正常生成。
   行为正确但会"意外"消耗配额（本机每小时 20 次）→ 记录为已知行为。
3. **首次请求冷启动**：healthz 首请求 416ms（动态目录抓取/代理预检预热），后续正常。

## 优化建议（按优先级）
1. **流式优先**（已支持）——客户端用 stream=true 避免长时间等待，网关已透传 reasoning/text 增量
2. **本机直连配额保护**：建议加启用直连兜底时的本机出口限流计数（已由 hourly_per_ip 语义部分覆盖）
3. **连接池复用**（Suggestions）：代理请求每次新建 reqwest Client，后续可池化
4. **超时分层**：上游 120s 读超时合理；客户端侧可自行设更短超时
