## 2. 关键观察与真实证据

### 2.1 上游 429：未遇到（重点结论）
- 全部到达上游的对话调用均为 **200**；`tryingopen_upstream_errors_total`（按 type 计）在所有运行窗口均为 **0**。
- 所有出现的 429 均为**网关自身按 key 限流**产生（`Retry-After` ≈ 3600s 窗口剩余秒数），非上游 429。上游 tryingopen.com 未对本机出口返回过 429/5xx。

### 2.2 限流语义（实测发现）
- 限流器按 **API key 跨端点（chat/messages/responses）共享窗口配额**：run-1 中 T4/T5/T6/T7 四个 200 后，第 5 次带 key 调用（T9 首次循环）即返回 429 + Retry-After: 3581。
- 若按任务原文「同 key 连续打 /v1/chat/completions 第 5 次应 429」理解：由于 T4/T5 已消耗 2 次，第 3/4 次 chat 由 T9 循环的第 1/2 次命中（分别计为第 5/6 次 keyed 调用），实际循环第 1 次即 429。**429+Retry-After 断言成立**。

### 2.3 熔断实测（发现产品行为）
- `bad/model-nonexistent` → 200，fallback 到 `deepseek/deepseek-v4-flash-0731`（真实上游生成了内容）。**未知模型被静默替换，客户端无处感知**。
- 因此「坏模型触发 5xx → 熔断 OPEN」在 v0.1.11 中**不可达**；熔断器正确性（503 保护、HALF_OPEN）需用其他 5xx 来源（如上游故障/超时）才能验证，本轮未观察到。
- 熔断器本身未出现误触发（无 5xx 计数）。

### 2.4 客户端环境注意（如实记录）
- PowerShell 5.1（`powershell.exe`）的 `HttpWebRequest` 对网关请求出现 **401**（相同请求、相同 key 头），而 PowerShell 7（`pwsh`）同一代码 **200**。判定为 PS 5.1/.NET Framework 客户端侧差异（HTTP 栈/头处理），非服务端缺陷；本报告证据均以 pwsh 7 结果为准。建议 API E2E 一律用 pwsh 7 / curl。
- 服务进程 stdout/stderr 经 `Start-Process -RedirectStandardOutput` 落盘为 0 字节（Windows 重定向缓冲未刷盘），故服务日志未采信；功能证据全部取自 HTTP 响应与 /metrics。

## 2.3 T10/T11 判定更正（主控复核）

T10/T11 的「FAIL」经主控复核为**测试假设与产品文档行为不符**，非产品缺陷：

- `docs/API_CONTRACT.md:115` 明确记载「模型不存在自动降级：请求未知模型 → 自动 fallback 到默认模型并正常回答（不报错）」。
- 因此 `bad/model-nonexistent` 返回 200 + fallback 模型是**文档化预期行为**，不是 bug。
- 熔断（CircuitBreaker）设计只在**上游真实 5xx** 时触发（`src/api.rs` 仅 `is_server_error()` 计失败）；未知模型走本地 resolve fallback，永不产生上游 5xx，故该路径不会触发熔断——符合设计。
- 若要验证熔断，应模拟真实上游 5xx（如不可达上游/超时），而非未知模型；这不在无 mock 约束下可稳定复现，故如实记录为 EXPECTED 而非伪造 PASS。
